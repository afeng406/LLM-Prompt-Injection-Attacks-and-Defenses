# AI 编程 Harness

此目录定义 AI 协作开发时的约束，只管理规则与边界。项目根目录的 [`AGENTS.md`](../AGENTS.md) 是工作入口，领域归属和依赖方向见 [`领域边界.md`](领域边界.md)。功能目标与实验判定见 [`实施方案.md`](../实施方案.md)，实际完成度见 [`实现记录.md`](../实现记录.md)；模型渠道的可变事实仍须结合账户核查。

## 每次编码的最短流程

1. **定位领域**：先说明改动属于问答执行、实验编排、评估或前端展示中的哪一处；涉及多个领域时列出唯一的数据拥有者和需要跨越的接口。
2. **定义完成标准**：写出可观察的输入、预期输出、失败情形和验证方式；无法验证的外部条件标明“未验证”。
3. **按最小范围实现**：只创建当前功能实际使用的文件与依赖。已有一个调用方时直接实现，出现多个真实调用方且规则相同时再抽取；不为假想扩展建立抽象层。
4. **检查耦合**：前端只看 HTTP 合同；模型 SDK 只在后端适配处出现；API 页面和评估脚本走同一个问答流程；评分规则不回流进模型提示词。
5. **验证并交付**：运行与改动相称的检查，报告实际结果、未覆盖的真实模型/浏览器验证、接口或实验版本变化。

## 对新业务的判定

新增一项业务时，先确定它是否有自己的规则、数据和验收标准。如果只是现有问答流程的一步，把逻辑留在现有模块；如果确实独立，再定义一个小接口和单向依赖。不要把不同业务塞进通用 `utils`、`common` 或“万能服务”，也不要把每个文件都包装成独立领域。

实验资料中的重复业务事实是**控制变量**：一份干净资料与 A07/A08/A09 三份污染资料需保持相同事实主体，差异是各自攻击载荷。它们可以重复保存，但必须在正式批次前核对内容与 hash；不要为了消除文本重复而在运行时动态拼接或改写资料。
